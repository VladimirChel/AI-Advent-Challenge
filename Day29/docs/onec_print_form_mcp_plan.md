# План реализации MCP-инструмента для печатных форм 1С

## Цель

Добавить в проект MCP-инструмент, который по типу и номеру документа запрашивает печатную форму из `1С:Предприятие` через HTTP-сервис и возвращает результат в удобном для клиента виде.

Базовый сценарий:

1. Клиент вызывает MCP tool `get_document_print_form`.
2. Инструмент валидирует входные параметры.
3. Инструмент обращается к HTTP-сервису 1С.
4. 1С ищет документ и формирует печатную форму.
5. Инструмент возвращает файл, base64-представление или ссылку на временный локальный файл.

## Что считаем результатом

Готовое решение должно уметь:

- принимать тип документа и номер документа;
- при необходимости уточнять дату, организацию и имя печатной формы;
- безопасно вызывать HTTP-сервис 1С;
- корректно обрабатывать `pdf`, `html` и `base64`;
- возвращать понятные ошибки, если документ не найден, найден не один документ или сервис 1С недоступен.

## Предлагаемый MCP-контракт

Имя инструмента:

- `get_document_print_form`

Описание:

- Получает печатную форму документа из 1С по типу и номеру документа.

### Входные параметры

```json
{
  "document_type": "sales_invoice",
  "document_number": "00001234",
  "document_date": "2026-04-29",
  "organization": "ООО Ромашка",
  "print_form": "invoice",
  "output_format": "pdf",
  "save_to_file": false
}
```

Обязательные поля:

- `document_type` — внешний код типа документа, понятный MCP-клиенту.
- `document_number` — номер документа в 1С.

Необязательные поля:

- `document_date` — дата документа в формате `YYYY-MM-DD`.
- `organization` — организация или иное уточнение для поиска.
- `print_form` — имя печатной формы, если у документа их несколько.
- `output_format` — ожидаемый формат ответа: `pdf`, `html`, `raw`.
- `save_to_file` — сохранить результат во временный файл на диске и вернуть путь.

### Выходные данные

Вариант для файла:

```json
{
  "ok": true,
  "document_type": "sales_invoice",
  "document_number": "00001234",
  "print_form": "invoice",
  "mime_type": "application/pdf",
  "filename": "SalesInvoice_00001234.pdf",
  "content_base64": "<base64>",
  "saved_path": null,
  "source": "1c_http_service"
}
```

Вариант при сохранении на диск:

```json
{
  "ok": true,
  "document_type": "sales_invoice",
  "document_number": "00001234",
  "print_form": "invoice",
  "mime_type": "application/pdf",
  "filename": "SalesInvoice_00001234.pdf",
  "content_base64": null,
  "saved_path": "output/print_forms/SalesInvoice_00001234.pdf",
  "source": "1c_http_service"
}
```

Вариант ошибки:

```json
{
  "ok": false,
  "error_code": "document_not_found",
  "message": "Document sales_invoice 00001234 was not found in 1C.",
  "details": {
    "document_type": "sales_invoice",
    "document_number": "00001234"
  }
}
```

## Предлагаемый контракт HTTP-сервиса 1С

Если сервис 1С еще не зафиксирован, лучше сразу договориться о `POST` с `JSON`.

### Запрос

`POST /hs/print-forms/get`

```json
{
  "documentType": "РеализацияТоваровУслуг",
  "documentNumber": "00001234",
  "documentDate": "2026-04-29",
  "organization": "ООО Ромашка",
  "printForm": "СчетФактура",
  "format": "pdf"
}
```

### Успешный ответ

```json
{
  "success": true,
  "mimeType": "application/pdf",
  "fileName": "СчетФактура_00001234.pdf",
  "contentBase64": "<base64>"
}
```

### Альтернативный успешный ответ

Если 1С удобнее сразу отдавать бинарный поток:

- `Content-Type: application/pdf`
- `Content-Disposition: attachment; filename="СчетФактура_00001234.pdf"`

Для Python-клиента лучше поддержать оба варианта:

- JSON с `contentBase64`;
- прямой бинарный HTTP-response.

### Ошибки сервиса 1С

Рекомендуемые коды:

- `400` — неверные параметры запроса;
- `401` или `403` — ошибка авторизации;
- `404` — документ не найден;
- `409` — найдено несколько документов;
- `422` — печатная форма недоступна для документа;
- `500` — внутренняя ошибка 1С;
- `503` — сервис временно недоступен.

## Маппинг типов документов

Наружу лучше не отдавать внутренние имена объектов 1С. Нужен словарь соответствий:

```json
{
  "sales_invoice": "РеализацияТоваровУслуг",
  "customer_order": "ЗаказКлиента",
  "payment_in": "ПоступлениеБезналичныхДенежныхСредств"
}
```

Отдельно можно держать маппинг печатных форм:

```json
{
  "sales_invoice": {
    "invoice": "СчетНаОплату",
    "act": "АктОбОказанииУслуг",
    "updk": "УПД"
  }
}
```

## Логика обработки запроса

1. Принять входные параметры MCP-инструмента.
2. Проверить обязательные поля `document_type` и `document_number`.
3. Убедиться, что `document_type` входит в whitelist.
4. Преобразовать внешний `document_type` в внутренний тип 1С.
5. При наличии `print_form` преобразовать его в внутреннее имя макета.
6. Собрать HTTP-запрос к 1С.
7. Выполнить вызов с таймаутом и безопасным логированием.
8. Разобрать ответ:
   - JSON с `contentBase64`;
   - бинарный `pdf/html`;
   - ошибка с кодом.
9. При `save_to_file=true` сохранить файл в `output/print_forms`.
10. Вернуть структурированный результат в MCP-клиент.

## Обработка ошибок

Нужно явно различать:

- `validation_error` — обязательные поля не переданы или формат некорректен;
- `unsupported_document_type` — тип документа не разрешен;
- `unsupported_print_form` — неизвестная печатная форма;
- `document_not_found` — документ не найден в 1С;
- `multiple_documents_found` — найдено больше одного документа;
- `print_form_not_available` — печатная форма не поддерживается;
- `authentication_failed` — ошибка авторизации в 1С;
- `upstream_timeout` — истек таймаут запроса;
- `upstream_unavailable` — 1С не отвечает;
- `unexpected_response` — сервис вернул неподдерживаемый формат.

## Безопасность

Минимальные требования:

- не логировать пароль, токен и полный base64-контент;
- ограничить допустимые `document_type`;
- не позволять произвольный URL из пользовательского запроса;
- ограничить размер ответа, чтобы не забрать слишком большой файл;
- нормализовать имя сохраняемого файла;
- по возможности писать audit log с датой, типом документа и результатом запроса.

## Тестовый набор

Минимум нужны такие сценарии:

1. Успешное получение `pdf` в `content_base64`.
2. Успешное получение `pdf` с сохранением в файл.
3. Успешное получение `html`.
4. Ошибка `404 document_not_found`.
5. Ошибка `409 multiple_documents_found`.
6. Ошибка авторизации.
7. Таймаут HTTP-запроса.
8. Некорректный `document_type`.
9. Бинарный ответ вместо JSON.
10. JSON без ожидаемых полей.

### Этап 3. Реализовать модели и клиент 1С

### Этап 4. Реализовать MCP tool handler

Сделать отдельную функцию-обработчик `get_document_print_form`.

### Этап 5. Добавить файловое сохранение результата

Сохранять печатные формы в отдельную директорию `output/print_forms`.

### Этап 6. Покрыть тестами

Сделать unit-тесты на маппинг, парсинг и обработку ошибок.

### Этап 7. Провести интеграционную проверку

Проверить на реальной базе 1С хотя бы:

- один тип документа;
- две разные печатные формы;
- кириллицу в имени файла;
- бинарный и JSON-варианты ответа.

## Критерии готовности

Считать задачу завершенной, когда:

- MCP tool принимает запрос по типу и номеру документа;
- документ успешно находится в 1С;
- печатная форма возвращается в `pdf` или `html`;
- ошибки возвращаются в нормализованном формате;
- конфигурация вынесена в `.env`;
- есть автоматические тесты на базовые сценарии;
- результат проверен на реальном HTTP-сервисе 1С.

## Что лучше уточнить до старта кода

Есть три важных места, где без согласования легко сделать неверную реализацию:

1. По номеру документа в 1С поиск точно уникален или нужен еще `date` и `organization`.
2. Сервис 1С будет отдавать уже готовый `base64/json` или бинарный поток.
3. Нужен только `pdf` или также обязательна поддержка `html/xlsx`.
