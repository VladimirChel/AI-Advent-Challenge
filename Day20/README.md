# Фреймворк оркестрации Day20

`Day20` начинается с пустой директории, поэтому естественная точка интеграции здесь — не существующий API-слой внутри этой папки. Правильное решение — сделать `Day20` переиспользуемой библиотекой оркестрации, которую сможет использовать `Day12`, вместо того чтобы держать логику оркестрации встроенной в `llm/client.py`.

## Анализ текущей архитектуры

Текущий поток в Day12 выглядит так:

1. `api/generate.py` определяет настройки MCP и передает их в вызов LLM.
2. `llm/client.py` запускает MCP-сессии, объединяет списки инструментов, строит псевдонимы с пространствами имен, выполняет многошаговый цикл вызова инструментов и накапливает трассировку.
3. `llm/mcp_client.py` служит транспортным адаптером для MCP-серверов через `stdio`.

Это означает, что реальная граница для выделения находится между:

- нормализацией запроса в `api/generate.py`;
- оркестрацией модели и инструментов в `llm/client.py`;
- реализацией транспорта в `llm/mcp_client.py`.

## Целевая структура модулей

Фреймворк, реализованный в этой папке, организован так:

- `orchestration/types.py`: общие модели выполнения, инструментов, сообщений и трассировки.
- `orchestration/registry.py`: реестр серверов, пул серверов и реестр инструментов.
- `orchestration/router.py`: абстракция маршрутизации и стратегия промпта по умолчанию для маршрутизации инструментов.
- `orchestration/policies.py`: движок политик для максимального числа шагов, ограничений на сервер, антизацикливания, таймаутов и порогов частичных ошибок.
- `orchestration/planner.py`: планировщик оркестрации и цикл выполнения.
- `orchestration/openai_adapter.py`: совместимый с OpenAI адаптер модели для chat completions с вызовом инструментов.

## Реализованная часть фреймворка

Текущая часть намеренно небольшая, но рабочая:

- реестр серверов с нормализованными идентификаторами серверов;
- реестр инструментов с псевдонимами в пространстве имен в формате `server_id__tool_name`;
- абстракция маршрутизатора со стратегией маршрутизации по умолчанию для нескольких серверов;
- планировщик/цикл выполнения, отделенный от транспорта и клиента модели;
- модель трассировки выполнения со списком вызовов инструментов и структурированными событиями трассировки;
- политики для:
  - максимального числа шагов;
  - ограничений на каждый сервер;
  - таймаута по реальному времени;
  - частичных ошибок;
  - защиты от зацикливания при повторяющихся идентичных вызовах.

## Почему это подходит для Day12

Этот фреймворк отражает текущие обязанности Day12, но переносит их в отдельный слой:

- `Day12 llm/client.py` становится в основном адаптером и модулем связывания.
- `Day12 llm/mcp_client.py` остается конкретной реализацией MCP-транспорта.
- `Day12 api/generate.py` продолжает определять MCP-настройки на уровне запроса.

## План интеграции с Day12

Наиболее чистый следующий шаг интеграции:

1. Оставить `api/generate.py::resolve_mcp_settings` слоем нормализации запроса и конфигурации.
2. Заменить ручной цикл в `Day12/llm/client.py::call_chat_completion_with_mcp` на:
   - построение `ServerRegistry` из `MCPSettings.servers`;
   - тонкую фабрику сессий-обертку над `MCPClientSession`;
   - `OpenAIChatCompletionsModel`, оборачивающую существующий клиент `OpenAI`;
   - `Orchestrator.execute(...)`.
3. Сопоставить `ExecutionResult.trace` обратно с существующими полями `GenerateResponse`:
   - `mcp_used`;
   - `mcp_servers`;
   - `mcp_tools_offered`;
   - `mcp_tool_calls`;
   - `mcp_tool_trace`.

## Предлагаемая форма адаптера Day12

Адаптер на стороне Day12 должен оставаться тонким и локальным для Day12:

```python
registry = ServerRegistry()
for server in resolved_servers:
    registry.register(
        server.id,
        lambda server=server: MCPClientSession(
            server.server_script,
            startup_wait_seconds=server.wait_after_start_seconds or 0.0,
            request_timeout_seconds=server.tool_call_timeout_seconds or 20.0,
        ),
    )

model = OpenAIChatCompletionsModel(
    client=openai_client,
    model=model_name,
    request_options={...existing completion params except messages/tools...},
)

result = Orchestrator(
    server_registry=registry,
    policy=ExecutionPolicy(
        max_steps=mcp_settings.max_tool_roundtrips or 4,
        max_calls_per_server=4,
        wall_clock_timeout_seconds=REQUEST_TIMEOUT_SECONDS,
        allow_partial_failures=True,
    ),
).execute(
    model=model,
    messages=[ChatMessage(role=m.role, content=m.content) for m in full_messages],
    metadata={"user": user_id},
)
```

## Архитектурная оценка

Поскольку у `Day20` не было существующей структуры приложения, наиболее естественным решением было реализовать фреймворк напрямую как библиотечный модуль. API- и web-слой должны оставаться вне этой папки. Слой оркестрации должен сохраняться библиотечным и переиспользуемым, а транспортные адаптеры и привязка конечных точек должны жить в потребляющих проектах, таких как `Day12`.
